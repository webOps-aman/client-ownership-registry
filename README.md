# Client Ownership Registry (frontend demo)

Company: **Emperium** (change it with `NEXT_PUBLIC_COMPANY_NAME` in `.env.local`).
Designed and developed by [ravan.ai](https://www.ravan.ai/).

A timestamped proof of **who registered a client first**. Real-estate clients are sourced by company agents,
the owner, or external brokers who earn commission. When a client visits a broker first and the company later,
commission disputes follow. This app settles that: **first valid registration wins.**

> **This is a FRONTEND-ONLY demo.** There is no backend and no database. All data lives in the browser
> (Redux Toolkit + localStorage) so a client can see a fully working product. The backend comes after approval.

---

## Quick start

Requires **Node.js 18.18 or newer**.

```bash
npm install
cp .env.example .env.local     # already included in the zip, edit values if you like
npm run dev
```

Open http://localhost:3000. The first run downloads the Fraunces and Inter fonts (needs internet once).

Other scripts: `npm run build` (production build), `npm start` (serve the build).

## A 5-minute demo script

1. **Admin overview.** Sign in as `admin`. Show the stat cards, recent registrations and activity.
2. **Check a client.** Sign out, sign in as `broker1`. Open *Check client* and search `98765 01002`
   (already registered). Note it reveals only the owner, owner type and date, never the client's name.
3. **Register a new client.** Search a new number, click *Register this client*, submit. Show the proof card
   with the record number and system timestamp (it can't be edited).
4. **Duplicate blocked.** Sign in as `broker2` and try to register that same number (try `+91 99999-11111`
   style variants too). It is blocked and logged.
5. **Admin follow-up.** Back as `admin`: *Duplicate attempts* -> *Create dispute* -> *Disputes* -> *Resolve*
   (try "Transfer to claimant"). Open *Audit log* to show every step. Export *Clients* to CSV.
6. **Reset.** *Settings* -> *Reset demo data* restores the sample data before the next presentation.

Sample clients (phone -> owner): `9876501001` broker1, `9876501002` agent, `9876501003` broker2,
`9876501004` broker3, `9876501005` broker1, `9876501006` agent.

## Roles and permissions

| Action | Agent | Broker | Admin |
|---|---|---|---|
| Check a client by phone (rate-limited) | Yes | Yes | Yes (no limit, via the clients table) |
| Register a client | Yes (source = Direct) | Yes (source = Broker) | No |
| See own registrations | Yes | Yes | n/a |
| See ALL clients, logs, disputes | No | No | Yes |
| Edit / transfer a client (reason required) | No | No | Yes |
| Manage brokers, disputes, settings | No | No | Yes |

## Business rules and where they live

All rules are in `src/services/` (not in components), so they can't be bypassed by the UI.

| Rule | Implemented in |
|---|---|
| Phone is the identity: strip spaces/dashes/brackets, accept `+91`/`91`/`0`, compare last 10 digits | `utils/phone.js`, `clientService` |
| First valid registration wins; duplicates blocked, logged, shown to Admin | `clientService.register` |
| Timestamp is generated by the app, never by the caller | `clientService.register` (`createdAt`) |
| Brokers/agents only see their own records; check returns owner name, type and date only | `clientService.list` / `check`, `logService.list` |
| Search rate limit (default 10 per minute per user, admin exempt) | `clientService.check`, `hooks/useRateLimit.js` (UI) |
| Every action goes to the audit log | `logService.audit`, called by every service |
| Admin edit/transfer needs a reason; previous owner kept in `history` | `clientService.update` / `transferOwnership` |
| Optional ownership expiry (`expiresAt`) | In the data model, **not enforced** |

## Project structure

```
src/
  app/            routes: login, dashboard/ (agent+broker), admin/ (admin only), loading.jsx + error.jsx per area
  components/     ui/ (design system), layout/, guards/, dashboard/, admin/
  services/       the ONLY data layer (storage.js is the only file touching localStorage)
  store/          Redux Toolkit: slices, thunks, selectors, tab sync
  config/         env.js (the ONLY file reading process.env), constants.js, navigation.js, auditMeta.js
  hooks/          useAuth, useDebounce, usePagination, useRateLimit
  utils/          phone, date, id, csv
  data/           demo seed data
```

Data flow: `component -> dispatch(thunk) -> service -> storage -> localStorage`, then the store reloads from the
services so the UI always matches what was saved. Slices hold only what the signed-in user may see.

## Design system

Every color, font size, shadow, radius and spacing value is a token in `tailwind.config.js`; components use the
tokens only. Fonts: Fraunces (headings) and Inter (UI) through `next/font`. A live preview of the base
components is at `/design-preview` (delete `src/app/design-preview/` before a client presentation if you like).

## Performance

- `dashboard/` and `admin/` are separate route segments, so brokers never download admin code.
- Tables, modals and dispute dialogs load with `next/dynamic` and skeleton fallbacks; the CSV code loads on click.
- `loading.jsx` per route, memoized selectors (`createSelector`), debounced search, `React.memo` on list rows.

## Data storage notes

- Keys are prefixed `cor_v1_` (session, users, clients, attempts, searches, audit, disputes, meta).
- localStorage is **per browser**. To demo several roles, use the same browser (one tab per role works; tabs stay in sync).
- Logs are capped at 2,000 entries each to stay under the ~5 MB browser limit.
- *Settings -> Reset demo data* wipes and reseeds everything.

## How to replace localStorage with a real backend later

The UI only talks to **thunks**, and thunks only talk to **services**. So the migration is: rewrite the files in
`src/services/` to call your API. Components, slices, selectors and pages stay as they are.

### 1. Service -> endpoint map

| Service function | Suggested endpoint |
|---|---|
| `authService.login / logout / restore` | `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` |
| `userService.list / add` | `GET /api/users`, `POST /api/users` |
| `userService.setStatus / resetPassword` | `PATCH /api/users/:id/status`, `POST /api/users/:id/reset-password` |
| `clientService.list` | `GET /api/clients` (admin: all, others: only their own) |
| `clientService.check` | `POST /api/clients/check` (returns only owner name, type, date) |
| `clientService.register` | `POST /api/clients` |
| `clientService.update / transferOwnership` | `PATCH /api/clients/:id`, `POST /api/clients/:id/transfer` |
| `logService.list` | `GET /api/logs/attempts`, `/searches`, `/audit` |
| `disputeService.list / create / resolve` | `GET /api/disputes`, `POST /api/disputes`, `POST /api/disputes/:id/resolve` |

Example, `register` before and after (same signature, so nothing else changes):

```js
// BEFORE (demo): src/services/clientService.js
async register(user, form) { /* validate, check duplicates in localStorage, save */ }

// AFTER (real API)
async register(user, form) {
  const res = await fetch("/api/clients", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    credentials: "include",
    body: JSON.stringify(form),
  });
  const data = await res.json();
  if (!res.ok) throw new AppError(data.code, data.message, data); // keep the same error codes
  return data;
}
```

Keep the same error codes (`DUPLICATE`, `RATE_LIMITED`, `VALIDATION`, `INVALID_PHONE`, `FORBIDDEN`...) because the
UI reacts to them. The functions `logService.audit / search / attempt` are called *inside* other services today;
on a backend they become server-side side effects of the endpoints above (write them in the same transaction).

### 2. What the backend must enforce (the demo only simulates these)

- **Uniqueness:** a unique index on the normalized phone (for MongoDB, a partial unique index on
  `phoneNormalized` where `status` is `active`). The database, not the app, decides who registered first.
- **Timestamps:** set `createdAt` on the server. Never accept it from the client.
- **Check endpoint:** return only owner name, owner type and registered date; rate-limit per user on the server
  (for example `express-rate-limit` or a counter collection).
- **Authorization:** role middleware on every route; non-admins get only their own clients and logs.
- **Authentication:** hashed passwords (bcrypt), a JWT or session in an `httpOnly` cookie, and **no credentials
  in env vars shipped to the browser**. Delete the `NEXT_PUBLIC_*_ID/PASSWORD` variables.
- **Audit log:** written server-side for every action, including login and logout.

### 3. Cleanup checklist

1. Rewrite each file in `src/services/` (keep function names and return shapes).
2. Delete `services/storage.js`, `services/seedService.js`, `data/`, and the *Reset demo data* card.
3. Remove `demoUsers` from `config/env.js` and the demo credentials box from the login page.
4. Optional: add Next.js `middleware.js` for server-side route protection (the client-side guards stay as a UX layer).
5. `hydrateStore` currently reloads everything after each action; with a real API you can switch to updating
   just the affected slice or refetching only what changed.

## Future: GoHighLevel integration (not built)

The plan is to push each newly registered client to GoHighLevel (create or update a contact, tagged with the
owner and source), likely as a server-side call right after `POST /api/clients` succeeds, so API keys never reach
the browser. Admin *Settings* already has a "Coming soon" card as the placeholder. Nothing is implemented yet.

## Known limitations of this demo

- Passwords are plain text in localStorage and demo credentials are readable in the browser bundle.
- Rate limiting and "first registered wins" are enforced in the browser, so a user who clears their storage resets them.
- Data is per browser; there is no sync between devices.
- Roles are enforced in the UI and service layer, but a technical user can edit localStorage. A backend fixes this.
- No Manager / Team Lead role and no ownership-expiry enforcement in this phase.
